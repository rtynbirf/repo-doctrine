## T01 · СВОД-раунд 4 — предложение «СВОД как SBOM аккаунта»

**Мир:** CISA «2026 Minimum Elements for SBOM» — инвентарь обязан быть машинно-читаемым, иметь автора/потребителя/распространителя и поддерживать аттестации VEX (cisa.gov/topics/.../sbom). Каталоги данных 2026 требуют автометадаты и lineage (toolsfordata.com, «37 Best Data Catalog Tools — 2026»). Ручной HTML-каталог без машинного слоя — прошлая эпоха.

**Своё:** СВОД получает двойную правду — `account-sbom.json` (машина: 41 репо, кластер, статус, хеш HEAD, дата пуша, license, роль агента) генерится скриптом из живого API, а `edinyy-svod-v*.html` строится **из этого JSON**, а не параллельно с ним. Числа в HTML — то же, что в JSON, всегда. Каждая репа-строка несёт `head_sha` — это VEX-подобная аттестация «состояние на дату». Универсально: механизм работает для любого аккаунта; сингулярно: СВОД остаётся автономным одним файлом (шрифты вшиты, ноль запросов) — JSON вшивается в HTML как data-слой.

**Приёмка:** `jq '.repositories | length' account-sbom.json` == 41; SHA256 всех `head_sha` сходится с живым API в момент сборки; HTML содержит те же 41 строки (grep по сгенерённым якорям).

## T02 · Профиль v5 — предложение «Числа, которые сами себя пишут»

**Мир:** self-updating README на GitHub Actions — мейнстрим (lowlighter/metrics — 30+ плагинов, Action коммитит SVG обратно; dev.to, Medium-гайды 2025–2026). Лучшие профили вообще не содержат ручных чисел.

**Своё:** в профиле `rtynbirf` — Action `truth-cron` (раз в ночь): по живому API считает репы/коммиты/топ-языки и переписывает одну строку README между маркерами `<!-- truth:start -->…<!-- truth:end -->`. Никто руками числа не пишет — потому никто и не может соврать. Строка падает, если API недоступен — коммита нет (журнал не лжёт: нет данных = нет утверждения). Универсально: маркеры применимы в любом README; сингулярно: числа сопровождаются SHA256-хешем среза API прямо в строке-комментарии.

**Приёмка:** после прогона Action `git log` содержит коммит `truth-cron`; между маркерами нет захардкоженных чисел; `grep -c 'truth:' README.md` == 1.

## T03 · Карта-дельта — предложение «Карта как код + drift-детектор доктрины»

**Мир:** Terraform GitHub provider — настройки репо как код; drift detection по расписанию с алертом — стандарт (developer.hashicorp.com; гайды GitHub Actions 2025–2026). Policy-as-code: preconditions + policies.

**Своё:** `account-state.json` в доктрине — декларативное состояние аккаунта (какая репа существует, видимость, дефолт-ветка, has_issues, лицензия, архив-флаг). Еженедельный Action-сверка (геррит-аналог guardian-tripwire для целой учётки): живой API vs JSON — расхождение автоматически открывает issue «DRIFT: …» с точным диффом. Карта 06 перестаёт быть снимком и становится **тезисом, который проверяется**. Универсально: то же, чем guardian-tripwire охранял историю, теперь охраняет конфигурацию; сингулярно: JSON живёт в доктрине рядом с правилами — карта и закон в одном коммите.

**Приёмка:** сверка-скрипт на живом аккаунте выводит `0 drift`; тест на искусственное расхождение (удалить строку из JSON) — issue открылось и закрылось по факту исправления.

## T04 · tool-catalog в agryp — предложение «Каталог как данные, а не как список»

**Мир:** awesome-list стандарты (критерии, лейблы, единый формат строки); data-package подход (schema + данные, валидация) —см. datapackage.json в собственном `global-video-platforms-registry`; in-browser CSV-schema инспекторы (awesomeCSV).

**Своё:** 2444 позиции не просто влить — каталогу задать **схему** (`docs/tool-catalog.schema.json`: id, категория, статус «проверен/не проверен», хеш-версия среза, источник) и кросс-ссылки с `polymath-tools-atlas` (665 инструментов): пересекающиеся инструменты получают общий `tool_id`, каталоги сшиваются в одну сеть без дублирования правды. Это превращает два каталога в **двухглазое зрение роя** (машинный CSV + экспозиция ГОЛОГРАММА). Универсально: схема применима к любому каталогу аккаунта; сингулярно: agryp становится не только процессным слоем, но и станком инструментов.

**Приёмка:** CSV валидируется схемой (jsonschema — 0 ошибок); число пересечений с tools-atlas считается скриптом и напечатано в README каталога; статус «проверен» не ставится без источника.

## T05 · PR#5 cell-swarm — предложение «Геном как сервис-реестр»

**Мир:** Consul service catalog / k8s Service Catalog — инвентарь сервисов декларативен и сверяем (developer.hashicorp.com/consul; InfoQ по Service Catalog CRD). Реестр — не документ, а структура данных с проверкой регистрации.

**Своё:** запись клетки в геноме cell-swarm получает **инвариант регистрации**: пин клетки (commit SHA agryp) должен резолвиться в живой репо, а `overseer`-поле — в живой файл-договор agryp. Действие: к PR#5 добавить пин на текущий HEAD (после T04) + CI-проверку «клетка резолвится», затем влить. Дальше — правило для всех будущих клеток: геном не принимает запись, если цель не резолвится. Универсально: любой реестр роя (пиры commons, клетки) получает один и тот же резолвер; сингулярно: геном становится тем, чем и должен быть — исполняемой картой роя, а не справкой.

**Приёмка:** CI cell-swarm содержит job «genome-resolve»: все клетки в геноме резолвятся по живым HEAD; PR#5 влит после зелёного резолва.

## T06 · agryp виток 10 — предложение «Метрики как .prom, журнал с печатью, договор с подписью»

**Мир:** ① node_exporter textfile collector — признанный способ отдавать метрики **файлами** (`.prom` текст, атомарная запись rename — github.com/prometheus/node_exporter) — Prometheus читает файл, ноль сокетов на стороне экспортёра; ② journald: ротация по размеру (SystemMaxFileSize) + forward-secure **sealing** журнала ключом печати (гайд «Protecting journald — forward append-only logs and seal», 2026) — журнал доказуемо не переписан задним числом; ③ audit trail: кто изменил конфиг — обязательное событие.

**Своё (ядро витка 10 три суммы одной формулы):** ① экспорт метрик agryp — **в формате .prom**: `agryp_metrics_total{unit="…"} …` — ноль сокетов (Ст. 13 не тронута), но формат сразу читается мировым инструментарием (универсально!); ② журнал-ротация — отрезание хвоста пломбируется **печатью-цепью**: последняя запись содержит sha256 предпоследней (хеш-цепь, как байт-цепь cell-rs), поэтому «затереть историю» становится машинно-обнаружимым — это мировой forward-sealing, доведённый до файлов-как-API; ③ сигнатуры юнитов — при reload журнал пишет `unit-sign` с хешем договора и mtime — «кто менял» в смысле «что именно поменялось» (дифф двух хешей), а не «кто» (агентов не различаем — названо вслух).

**Приёмка:** `make demo-metrics` — файл `.prom` валиден grepp'ом на формат и совпадает с журналом; `make demo-rotate` — цепь хешей проверяется скриптом аудита на 10 ротациях, попытка подделать середину цепи ловится с точным приговором; `make demo-sign` — подмена договора между reload-ами отражена событием `unit-sign`; регрессия витков 1–9 rc=0, сироты 0.

## T07 · commons wave34 — предложение «ConsentGrant как ReBAC роя»

**Мир:** OpenFGA (CNCF, Zanzibar) — доступ как отношения (ReBAC): не «список прав», а граф «кто→связь→что», машинно проверяемый (openfga.dev/docs/authorization-concepts).

**Своё:** волна №34 не просто вливается — ConsentGrant описывается отношениями генома: «агент→действие→ресурс» — то же отношение, что клетка→обязанность→окно. Проверку цепочек согласий отдаём **task-graph-propagator** (он уже умеет полукольца и пропагацию): согласие — факт на графе задач, «нет пути в графе» = отказ. Эмерджентная связка: три репы (commons, cell-swarm, task-graph-propagator) образуют одну машину воли: клетка просит → граф проверяет → геном фиксирует. Универсально: схема отношений работает для любых будущих согласий; сингулярно: пропагатор — уже свой, ноль новых зависимостей.

**Приёмка:** в main commons — ADR-0017 с моделью отношений; тест-скрипт: 3 сценария (разрешено/отказано/неопределено UNKNOWN≠FALSE) решаются пропагатором; wave34 влита, CI зелёный.

## T08 · voice-atlas proven-recipes — предложение «Рецепт = аттестация вход-выход»

**Мир:** MLflow Dataset Tracking и DVC — воспроизводимость через хеши датасетов и lineage (mlflow.org/docs/latest/ml/dataset; DVC+SageMaker lineage 2026). Рецепт без хешей входов — не рецепт, а надежда.

**Своё:** proven-recipes переезжает из «ветки-отложения» в **аттестационный формат**: каждый рецепт (Task 18 и др.) получает `RECIPE.manifest` — вход-хеши (whisper-транскрипты, wav-файлы, инструменты с версиями) → выход-хеши (строфы на 20 языках). Rebase ветки за 27 коммитов выполняется после манифестов — манифесты ловят порчу wav на этапе rebase (CRLF-ловушка становится не запретом, а проверкой). Универсально: формат «вход-хеш → выход-хеш» повторит то, что PHOENIX уже делает Law 4, — один канон доказательства на весь аккаунт; сингулярно: RUVSON поёт только то, чей байт-путь имеет хеш.

**Приёмка:** ветка rebased+влита; `RECIPE.manifest` каждого рецепта валидируется (вход-хеши == факт в дереве); CI гоняет «проверку хешей перед мерджем».

## T09 · PHOENIX proven-works — предложение «Пломбы по SLSA: subject+digest без инфраструктуры»

**Мир:** SLSA v1.0/v1.2 — provenance это in-toto аттестация: subject (артефакт+digest), builder.id, resolvedDependencies (slsa.dev/spec). Уровни: даже Level 1 («provenance exists») уже поднимает доверие. Формат не требует серверов — это просто JSON.

**Своё:** бисекция 0.2-BISECT и все proven-works PHOENIX получают **свой SLSA-подобный предикат**: `work-attestation.jsonl` — `{subject: iso-file, digest: sha256, builder: "PHX-DISK-PREP v2.0", resolved: [10 хешей частей]}` — SEALS.jsonl поднимается до уровня, читаемого мировыми верификаторами (in-toto-совместимость без запуска инфраструктуры). Rebase proven-works за 111 коммитов идёт по хешам, а не по датам. Универсально: один предикат покрывает ISO, wav, gguf-части, архивы vault; сингулярно: аккаунт получает SLSA Level 1-эквивалент на своих собственных файлах-пломбах.

**Приёмка:** ветка влита; верификатор (10 строк sh/python) читает все аттестации main и подтверждает digests; попытка подменить digest ловится тестом.

## T10 · Dependabot-волна — предложение «Реновация как канал, а не как разовая волна»

**Мир:** Renovate vs Dependabot 2025–2026: SHA-pinning удовлетворяет OpenSSF Scorecard; Renovate сильнее в сохранении пинов, группировке обновлений и автомердже (microsoft/edge-ai issue #404, Renovate Bot comparison); Dependabot — GitHub-native и проще. Главный тренд — не «какой бот», а **минимум открытых хвостов** (0 stale PR) и групповые PR.

**Своё:** волна закрывается не «по одному» — **каноном обновлений**: ① Security-updates Dependabot — принимать всегда (7 PR из аудита); ② major-версии actions (checkout 4→7, setup-python 5→7) — группировать в один PR с прогоном регрессии всех реп (свой SHA-канон уже есть — «сверен живым ls-remote», это и есть Scorecard-практика); ③ зависшие ветки без PR (nous ×3, github-runbook ×1) — не resurrectить, а закрыть осознанно с записью в ворклог. Универсально: правило «хвостов ноль либо хвост с пломбой-объяснением» действует на все 41 реп; сингулярно: регрессию гоняет не каждый реп отдельно, а контур сверки аккаунта (T03-инфраструктура).

**Приёмка:** `issues?state=open` по 4 репам из аудита — 0 dependabot-хвостов; каждая закрытая ветка/PR имеет ворклог-строку с причиной; SHA-канон всех workflows перепроверен живым ls-remote.

## T11 · singulyar дефолт — предложение «Двухименная ветка и защитная пломба»

**Мир:** GitHub официально поддерживает rename дефолт-ветки (docs.github.com, включая API и редиректы), но для 1,58 ГБ репы с Pages и 767 коммитами истории переименование — операция с риском для внешних ссылок (пины,Pages source). Практика сообщества: осторожно, с фиксом локальных клонов.

**Приёмка:** карта содержит решение с датой и подписью Хозяина; workflow-пломба задеплоена; тестовый push в main порождает issue; хвосты `latka-c141-wip`, `minus-fond` закрыты с ворклог-записью.

## T12 · release-vault — предложение «3-2-1-1-0 для роя: учение восстановления раз в квартал»

**Мир:** 3-2-1 уже база; современный стандарт — **3-2-1-1-0**: +1 иммутабельная/air-gap копия и **0 ошибок при проверочном восстановлении** (Veeam, US Chamber 2025–2026: «Test your backup copies» — бэкап без учения не бэкап).

**Своё:** vault — уже шифрованная офсайт-копия (AES-256-CBC/PBKDF2-600k). Добавляется **учение**: раз в квартал контур сверки выбирает случайный релизный ассет, расшифровывает, байт-сверяет с исходником (или с хешем из SLSA-аттестации T09!) и пишет результат в PULSE.md. 0 расхождений = приёмка; находка расхождения = issue с планом. Эмерджентная связка: аттестации T09 дают vault эталонные хеши — учение проверяет не «файл открылся», а «байты совпали с доказанным». Универсально: правило 3-2-1-1-0 применимо ко всем тяжеловесам (singulyar 1,58 ГБ, ruvson-lyrics 526 МБ); сингулярно: учение — это обряд, а не скрипт: результат пишется в PULSE и в карту, день учения виден в истории.

**Приёмка:** сверка-скрипт покрывает 100% ассетов приватных реп (манифест = факт); квартальный drill даёт запись в PULSE.md «drill: N ассетов, 0 расхождений» (или issue).

## Эмерджентный синтез: «Пломба-контур»

Из двенадцати предложений складывается одна машина, которой не было ни в одном мировом гайде: **аккаунт, где каждая строка правды имеет хеш-происхождение** — SBOM-инвентарь (T01) строит профиль (T02), профиль сверяется drift-детектором (T03), каталоги сшиты общими id (T04), клетки резолвятся геномом (T05), ядро отдаёт метрики файлами с хеш-цепью журнала (T06), согласия проверяются графом (T07), рецепты и работы несут аттестации (T08/T09), обновления текут каналом с нулём хвостов (T10), аномалии узаконены и сигналят (T11), а резерв проверяется учением до нуля ошибок (T12).

Ни один компонент не нов для мира поодиночке. Ново то, что здесь они — **один организм на файлах и хешах, без серверов, сокетов и ручных чисел**: мировой стандарт качества, исполненный средствами одного аккаунта. Это и есть универсальное: любой аккаунт любого размера может скопировать контур целиком.

2. T01–T05 — волна A (P0): SBOM-генератор T01 делается первым — он кормит T02 и T03.
