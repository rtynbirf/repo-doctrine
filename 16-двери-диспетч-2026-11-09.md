# 16 · Дверь для каждой волны: workflow_dispatch обязателен у каждого schedule — линтер доктрины

**Реализует:** issue [#30](https://github.com/rtynbirf/repo-doctrine/issues/30) «Дверь для каждой волны» · **Пункт карты:** §2 Принципы · «workflow_dispatch на каждом schedule».

## Сингулярный ход (кратко)

«Дверь-линтер»: один читающий воркфлоу в repo-doctrine перечитывает YAML всех репо аккаунта и для каждого schedule без workflow_dispatch пишет вердикт `NO-DOOR {repo, file, cron}`. Роль doctrine_lint из issue #30 исполняет **wave3-door-lint** (имя волны ×3 — чтобы не пересечься с чужими волнами; append-принцип, ничего не переименовываем).

## Заложено этим коммитом (аддитивно)

| файл | роль |
|---|---|
| `.github/workflows/wave3-door-lint.yml` | крон `17 4 * * *` (04:17 UTC, вне топовых часов) + `workflow_dispatch` (дверь у самого линтера) + selftest-шаг |
| `scripts/lint_doors.py` | движок: обход репо → contents → raw-YAML → парсер `on:` → вердикт → job summary → append-issue с фрагментами патчей |

## Контракт парсера on: (stdlib, без PyYAML)

Линтер распознаёт дверь во всех трёх формах — это и есть критерий 3 из issue #30:

1. `on: [schedule, workflow_dispatch]` → дверь есть;
2. `on: {schedule: …, workflow_dispatch: {inputs: …}}` → дверь есть;
3. блочная `on:` с вложенным `workflow_dispatch:` → дверь есть.

Границы парсера (честно): строковый разбор, без полной грамматики YAML; блок `on:` кончается строкой с отступом ≤ его собственного (например `jobs:`), поэтому литералы `workflow_dispatch` внутри `run:`-скриптов не считываются. Все шесть форм из контракта зафиксированы selftest-фикстурами (`python3 scripts/lint_doors.py --selftest`, CI-safe, без сети).

## Бюджет вызовов API

- список репо: 1 вызов на страницу по 100 (`GET /users/{owner}/repos`);
- содержимое `.github/workflows`: 1 contents-вызов на репо (плюс работа с 403/404 без падения);
- тексты YAML — по raw-ссылке (`download_url`), **вне core-квоты** API.

Итого — оценка из issue #30 (~60–80 вызовов на 41 репо / 133 воркфлоу) выдерживается с запасом: десятки вызовов core, остальное — raw.

## Слот «генератор патчей»

По вердикту линтер собирает в теле append-issue готовые YAML-фрагменты: блок `on:` с сохранёнными кронами файла и добавленной строкой `workflow_dispatch:`. Применение — отдельным append-коммитом ответственной волны; линтер в чужие репо не пишет никогда.

## Отчёт и append-only

- job summary: счётчики (репо / воркфлоу / с schedule / с дверью) + вердикт-таблица;
- непустой NO-DOOR → НОВОЕ issue в repo-doctrine на каждый полный проход (старые не правятся); пустой → строка «✅ Все двери на месте», без issue.

## Критерии приёмки (честно, статический коммит)

| № | критерий | статус | что заложено |
|---|---|---|---|
| 1 | точный список schedule-воркфлоу без двери из 133; после волны — пуст | partial | движок и отчётность готовы; точность даёт первый живой прогон (сети у агента нет) |
| 2 | сам линтер имеет workflow_dispatch и запускается вручную в любой момент | partial | дверь в wave3-door-lint.yml заложена; ручной прогон возможен после принятия коммита |
| 3 | ноль ложных срабатываний: обе формы распознаны как «дверь есть» | done | обе формы из критерия покрыты selftest-фикстурами (локальный прогон 6/6); живое подтверждение — первый прогон |

## Ограничение охвата (следующий прогон)

С `github.token` линтер видит только публичные репо; полный охват 41 репо (включая 15 приватных из issue #17) — через PAT-секрет, который задаёт владелец. Приватные без токена молча не считаются — счётчики репо/воркфлоу в summary показывают реальный охват прогона.
