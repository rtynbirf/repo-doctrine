# 03 · ТОКЕНЫ И СЕКРЕТЫ

## Главная мысль

Токен — это ключ от всего аккаунта, отлитый в строке. Кто удержал строку —
удержал аккаунт. Поэтому:

1. токен живёт **только** в локальном файле вне git-слежки;
2. токен **никогда** не попадает в код, коммиты, issues, скриншоты и **чаты**;
3. токен имеет срок жизни и владелец умеет его отозвать за 30 секунд.

## Закон живой пробы (№11, 2026-11-09)

Ключ, не доказанный живой пробой, для роя не существует. До первой операции
мандата:

```
# 1) жив ли ключ (код, не память)
curl -s -o /dev/null -w "%{http_code}\n" \
  -H "Authorization: Bearer $TOKEN" https://api.github.com/user
# 2) когда умрёт (дата смерти известна ДО рождения операции)
curl -s -D - -o /dev/null \
  -H "Authorization: Bearer $TOKEN" https://api.github.com/user | grep -i token-expiration
```

- **HTTP 200** — ключ жив; заголовок `github-authentication-token-expiration`
  даёт дату смерти, она записывается в отчёт мандата до работы.
- **401/403** — честный ноль: запроси выпуск нового ключа по правилам выше,
  не «подбирай форму» на живых операциях (грабля №2).
- Проба повторяется после каждой ротации и при любом подозрении; остаток
  лимита (`/rate_limit`) — часть пробы.
- Канон: `20-грабли…md` §2 закон №11, §3 касание №1, §4 машинная приёмка.
  Прецедент 2026-11-09 (TH-DOCT-04): проба до операций → 200, смерть 2026-12-08.

## Выпуск токена (только fine-grained)

Classic-токены не выпускать: они дают сразу всё и не умеют в тонкие права.

Путь: `Settings → Developer settings → Fine-grained tokens → Generate new token`.

| Поле | Как заполнять |
|---|---|
| Token name | Понятное имя: `mandate-repo-setup-2026-11` |
| Expiration | **Не длиннее 90 дней**. Разовая задача — 7 дней |
| Resource owner | `rtynbirf` |
| Repository access | `Only select repositories` — перечислить ТОЛЬКО нужные. «All repositories» — только если задача реально по всему аккаунту |
| Permissions → Contents | `Read and write` — для пуша файлов/кода |
| Permissions → Metadata | `Read-only` (ставится автоматически) |
| Permissions → Administration | `Read and write` — ТОЛЬКО если задача про настройки/защиту/создание репо |
| Permissions → Issues / Pull requests | по необходимости |

Минимальные наборы под типовые задачи:

| Задача | Нужные права |
|---|---|
| Пушить код/доки в конкретное репо | Contents RW + Metadata R |
| Настроить флаги/защиту/topics | + Administration RW |
| Создать репо | + Administration RW (аккаунт) |
| Писать в ворклог (contents API) | Contents RW на H-PE11-PHOENIX |

## Хранение

- Песочница/агент: файл вида `scripts/.tok-*`, `chmod 600`, в `.gitignore`
  (у нас уже так: `scripts/.tok*` игнорируется, а `scripts/.tok` снят с слежения).
- Windows у Хозяина: файл в профиле, например `%USERPROFILE%\.gh-token`,
  НИКОГДА в папке репозитория.
- Худшие места: код, `.env` в репо, чат, скриншот с открытым блокнотом,
  issue, комментарий в PR.

## УРОК 2026-11-01: токен в чате

При выдаче мандата токен был вставлен в чат прямым текстом. Это удобно
ровно один раз и опасно навсегда: чат — не сейф, копия строки остаётся в
истории переписки и логах.

**Правило «засветился — ротация»:**

1. Работы по мандату завершены, токен больше не нужен → Хозяин идёт в
   `Settings → Developer settings → Fine-grained tokens` → **Revoke**.
2. Выпускает новый по правилам выше (короткий срок, узкие права).
3. Агенту передаётся **путь к файлу** с токеном, а не сама строка.

Пока ротация не сделана, считать: токен, побывавший в чате, действителен,
но скомпрометирован; не использовать его после дедлайна задачи.

**Маршрут для агента в песочнице.** «Передай путь к файлу» работает,
когда агент на той же машине. Песочничный агент твой диск не видит —
чат остаётся единственным каналом. Тогда токен выдаётся как расходник:
срок 7 дней, права только на нужные репо, использован → Revoke в той
же сессии. Токен, побывавший в чате, не «живёт дальше» — он умирает
сразу после задачи, и это норма, а не авария.

## Действия при утечке (реальной или подозреваемой)

1. **Revoke немедленно**: `Settings → Developer settings → ... → Delete`.
   Отзыв убивает доступ мгновенно — это важнее расследования.
2. Аудит: `Settings → Security log` — что делали чужие сессии, когда, откуда.
3. Проверить незнакомое: `Settings → Applications → Authorized OAuth Apps`,
   `Deploy keys` в каждом репо, `Collaborators`.
4. Выпустить новый токен по правилам выше.
5. Записать случай в ворклог (без самой строки токена!).

## Страховка в репо

На публичных репо включены **secret scanning + push protection** (2026-11-01):
если попытаться запушить файл с токеном — GitHub отклонит push. Это второй
рубеж после человеческой дисциплины, а не замена ей.
